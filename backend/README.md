# Backend TData

Здесь находится серверная логика: получение расписаний, нормализация матчей,
сопоставление команд, подготовка выгрузки и проверка результатов. Backend работает
внутри серверной части Next.js и отдельных CLI-процессов; самостоятельного Express-сервера нет.
HTTP-маршруты находятся в `../frontend/src/app/api` и обращаются сюда через `@backend/*`.

## Карта модулей

| Каталог | За что отвечает |
| --- | --- |
| `src/imports/` | Выбор источника импорта и единый ответ вызывающему API. |
| `src/sources/` | Клиенты внешних сайтов, разбор их форматов и импортеры отдельных источников. |
| `src/normalizers/` | Преобразование страниц к общей модели турнира для каждой дисциплины. |
| `src/matches/` | Время матчей, удаление дублей, оценка качества и представление расписания. |
| `src/teams/`, `src/sync/` | Канонические имена, сопоставление команд и синхронизация идентификаторов. |
| `src/manualImport/` | Распознавание текста и изображений, очередь изображений и ручные привязки. |
| `src/adminTeams/` | Импорт справочника команд и предложения для сопоставления. |
| `src/adminUpload/`, `src/exporters/` | Формирование выгрузки, правила отправки и транспорт Admin API. |
| `src/results/khl/` | Ревизии протоколов КХЛ, привязки статистики, preview и подготовка доставки. |
| `src/tline/` | Фоновая проверка официального расписания относительно линии Admin. |
| `src/auth/`, `src/http/` | Авторизация, адрес клиента и правила исходящих HTTP-запросов. |
| `src/db/`, `src/config/` | Prisma-клиент, повтор временных ошибок и настройки приложения. |
| `src/cache/`, `src/proxy/`, `src/utils/` | Обслуживание кэша, выбор прокси и общие серверные функции. |
| `prisma/` | Схема PostgreSQL, последовательные миграции и начальные данные. |

## Как проходят данные

**Импорт турнира.** `imports/dispatcher.ts` выбирает адаптер. Для Liquipedia
`sources/tdata/liquipedia/importer/singlePage.ts` получает сырой снимок и возвращает
кандидатов матчей. `recursive.ts` объединяет главную страницу и подстраницы,
согласует команды, удаляет дубли и оценивает качество. Принятый снимок заменяет
прежнее расписание через транзакцию в `persistence.ts`: неудачная вставка не должна
оставлять турнир без старых матчей. Ухудшившийся результат сохраняет предыдущий
снимок, в том числе при принудительном обновлении: оно сбрасывает кэш источника,
а опубликованное расписание заменяется только после проверки качества.
В `options.ts` проверяется размер пакета подстраниц.

**Нормализация Liquipedia.** Публичные `normalizers/*Tournament.ts` управляют этапами,
а папки `dota2/`, `counterstrike/`, `leagueoflegends/`, `valorant/` содержат их реализацию:
`htmlMatches.ts` и `wikitextMatches.ts` извлекают кандидатов, `participants.ts` — участников,
`values.ts` задаёт локальные правила дат и названий, `subPages.ts` выбирает страницы стадий.
`matchIdentity.ts` сохраняет стабильные идентификаторы и правила удаления дублей;
у Dota 2 `matchCoverage.ts` отдельно согласует точность HTML и wikitext.
Общие wiki-примитивы остаются в `wikiText.ts`, DOM-типы — в `htmlTypes.ts`.

**Исходящие соединения.** `adminUpload/sendFixtPayload.ts` проверяет разрешённый
адрес и DNS через `http/outboundPolicy.ts`, затем `pinnedTransport.ts` соединяется
с проверенным IP. Исходное имя остаётся в Host и TLS SNI; redirect запрещён,
время и размер ответа ограничены. `proxy/healthProbe.ts` выполняет проверку через
CONNECT/SOCKS-agent и закрывает соединение при завершении или ошибке.

**Ручное распознавание.** `manualImport/parseRequest.ts` разбирает вход,
`aiParser.ts` и `ocrPipeline.ts` извлекают расписание, `imageBatch.ts` ограничивает
очередь и убирает повторы. `buildManualFixtPayload.ts` готовит данные выгрузки.
Общий OCR-worker получает задания последовательно, чтобы его параметры не
перемешивались между изображениями. До вызова нативного декодера `imageFormat.ts`
допускает только PNG, JPEG и WebP по сигнатуре байтов; MIME-заголовок не считается
доказательством формата. HEIF/AVIF в локальном OCR не обрабатываются.

**Проверка TLine.** `tline/jobs/` управляет очередью и временным владением задачей.
`../scripts/tline-worker.ts` продлевает аренду и вызывает `application/executor.ts`.
Исполнитель получает свежие матчи через `sources/` и `admin/`, использует
`comparison/` для сравнения и сохраняет снимки с результатами в транзакции.
Если Admin не настроен полностью, результат остаётся частичным. При потере аренды
worker должен прекратить работу; проверка владения также выполняется перед записью
доказательств. `mappings/` и `application/manualDecisions.ts` отвечают за ручные решения.

**Результаты КХЛ.** `results/khl/autoSync.ts` выбирает завершённые игры за период.
`repository.ts` сохраняет сырой протокол и нормализованную ревизию, не дублируя
одинаковое содержимое. `preview.ts` проверяет актуальность ревизии и подтверждённые
привязки. `delivery.ts` повторно сверяет просмотренную ревизию и хеш и создаёт
идемпотентную запись `PENDING`; сама эта функция не отправляет HTTP-запрос.

## Правила изменения кода

- Маршрут API разбирает HTTP, проверяет доступ и вызывает серверный сценарий.
  Алгоритм импорта или сравнения размещается в соответствующем домене backend.
- Специфичные для источника URL, HTML-селекторы и поля ответа остаются в его адаптере.
  Общие правила времени, качества и команд используются из `matches/` и `teams/`.
- Комментарии объясняют порядок этапов, причины ограничения и сохраняемые условия.
  Они не пересказывают каждый оператор. Изменение поведения требует обновить и комментарий.
- Схему меняют новой миграцией. Уже существующие миграции могут менять данные:
  например, нормализовать формат пляжного волейбола и незаполненные слоты сетки.
  Их применение и восстановление проверяются на отдельной БД.

## Проверка

Команды запускаются из корня проекта. Быстрые проверки: `npm run typecheck`,
`npm run lint`, `npm test`. Сценарии с настоящей БД находятся в `../tests/integration/`
и запускаются через `npm run test:integration`; проверка транзакционного поведения
на тестовом двойнике не заменяет этот запуск. Покрытие ядра TLine проверяется
командой `npm run test:tline:coverage`. Browser E2E находятся в `../tests/e2e/`.

Указанные команды описывают способ проверки, а не утверждают, что внешние источники,
production-БД или сервер уже проверены. Текущий результат аудита хранится в документации проекта.
